# BPM 0.9.3 Documentation Search And Local RAG Completion Backlog

Date: 2026-07-28

Target BPM version: `0.9.3`

Epic ID: `BPM093`

Release risk: high. This epic changes documentation build artifacts, browser search, local model
distribution and execution, runtime APIs, privacy and network boundaries, six-locale behavior, and
release validation.

This backlog completes the BPM documentation discovery and assistance layer. It replaces the current
hand-written linear browser scan only after a measured open-source search-engine comparison, then
adds a local, resource-bounded RAG assistant that answers free-form BPM questions, maintains a
bounded conversation, cites the exact published documentation it used, and refuses unsupported or
off-topic requests.

Product source, UI copy, README, changelog, and maintained documentation use English as the primary
product language. Maintainer chat may be Russian, but implementation copy remains English unless a
task is explicitly updating one of the six product locales. English is the source locale; `ru`,
`de`, `zh-CN`, `fr`, and `es-ES` remain human-reviewed peers with no silent English fallback.

## Scope Summary

- Target version: `0.9.3`; compact epic id: `BPM093`.
- Search outcome: select and integrate the best-fit OSI-licensed documentation search engine for
  BPM through a reproducible six-locale relevance, footprint, latency, operability, accessibility,
  CSP, offline, and maintenance benchmark. The current engine remains the control, not the assumed
  loser.
- RAG outcome: add local multilingual retrieval and a small quantized local language model behind a
  grounded chat experience. Normal operation must not require a GPU, hosted inference, telemetry,
  or internet access.
- Target hardware outcome: the complete local assistant runs on the maintainer baseline - Intel
  Core i5-7200U, two cores/four threads, AVX2, 7.1 GiB RAM, and no required discrete GPU - within
  explicit memory, disk, latency, and throughput budgets.
- Knowledge-update outcome: documentation changes rebuild versioned chunks and embeddings
  deterministically. RAG knowledge is updated by ingest and re-indexing; it is not represented as
  undocumented model-weight training.
- Conversation outcome: the assistant answers in the active/requested locale, follows bounded
  multi-turn context, asks for clarification when needed, distinguishes answer/abstain/refuse states,
  and provides resolvable citations to current BPM topics and anchors.
- Safety outcome: a deterministic pre-generation scope gate and retrieval-confidence gate restrict
  the assistant to BPM, supported Firefox enterprise policy/settings, installation, operation,
  schemas, profiles, import/export, validation, CIS, API integration, and product documentation.
  Off-topic requests do not reach generation.
- Optional web outcome: one explicitly enabled provider path may retrieve current external evidence
  from an approved domain/source policy. It is disabled by default, requires clear per-use network
  state, remains subject to the BPM scope gate, and never replaces local documentation authority.
- Product-documentation outcome: all six locale guides, search/chat help, model installation and
  resource guidance, privacy/network behavior, troubleshooting, screenshots, manifests, runbooks,
  README durable current-state copy, and release gates describe the shipped system.

## Current-State Assessment

- BPM currently publishes six DITA locale trees and serves a generated static documentation portal
  under `/help/`. FastAPI `/docs` remains the OpenAPI UI and must not be displaced.
- Search is implemented in `documentation/assets/theme/bpm-docs-search.js`. It downloads a full
  locale JSON index, normalizes a query, scans every document in the browser, adds fixed weights for
  identifier/title/alias/body substring matches, sorts the result set, and applies generated facets.
- The existing search contracts are valuable controls: deterministic per-locale generation,
  reviewed aliases, stable identifiers, bounded typo fixtures, facets, URL state, localized empty
  results, reproducibility, integrity checks, and offline/CSP behavior must not disappear during a
  migration.
- Current search budgets allow at most 170 documents and 4.1 MB per locale and use deterministic
  scan units instead of measured wall-clock latency. That approach is predictable but does not prove
  morphology, Chinese segmentation, relevance at documentation-growth scale, or old-laptop browser
  performance.
- Active documentation contracts deliberately forbid AI, RAG, embeddings, vector search,
  generative answers, runtime network search, and telemetry-backed learning. This was an explicit
  `0.9.0` boundary, not an accidental omission. `0.9.3` must replace it with a reviewed opt-in local
  AI contract before any AI path can ship.
- The documentation subsystem already separates hand-authored DITA, generated metadata, installed
  runtime artifacts, tests, and ignored build/report/cache output. RAG chunks, embeddings, model
  metadata, and generated indexes must follow the same source/artifact boundary.
- No local model lifecycle, model-license/checksum manifest, vector index, grounded-answer API,
  chat UI, multi-turn state, scope classifier, web-evidence adapter, or AI-specific release gate is
  implemented today.
- The maintained product locales are exactly `en`, `ru`, `de`, `zh-CN`, `fr`, and `es-ES`.
  Cross-locale fallback is not an acceptable substitute for retrieval or answer quality in a weak
  locale.
- The maintainer machine has an Intel Core i5-7200U CPU, 7.1 GiB RAM, and constrained available
  memory during normal development. Model load must therefore be lazy, concurrency bounded, and
  disable/unload behavior observable.

## Technology Research Starting Point

These are benchmark candidates, not preselected implementation decisions:

- Keep the current deterministic scanner as the relevance and compatibility control.
- Evaluate [Pagefind](https://pagefind.app/) as the leading fully static candidate. Its official
  documentation describes per-language indexes, explicit English/Russian/German/French/Spanish
  stemming, Chinese segmentation, rich filtering, chunked browser loading, and an MIT-licensed
  no-server deployment model.
- Evaluate [Meilisearch multilingual indexing](https://www.meilisearch.com/docs/capabilities/indexing/how_to/handle_multilingual_data)
  as a local-service comparison when its language-specific tokenization, typo tolerance, filtering,
  or future hybrid retrieval might justify an additional daemon. A service cannot win without
  meeting the old-laptop, offline, packaging, startup, and failure-isolation budgets.
- Evaluate [llama.cpp's local server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
  as the CPU/GGUF inference control because it supports quantized CPU inference, streaming chat,
  embeddings, reranking, bounded threads/context, and a small local HTTP boundary.
- Include the Apache-2.0 [Qwen3 0.6B GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF) and other
  sub-2B multilingual instruction candidates, plus [Gemma 3 1B](https://ai.google.dev/gemma/docs/core/model_card_3),
  only after license, six-locale answer quality, quantization, context, and CPU benchmarks. Model
  popularity is not acceptance evidence.
- Evaluate [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) as the
  compact embedding control: its model card declares a 12-layer, 384-dimensional, MIT-licensed
  multilingual model. Compare it with at least one currently maintained compact alternative.
- Compare an exact normalized-matrix vector scan with
  [sqlite-vec](https://github.com/asg017/sqlite-vec). The corpus is small enough that a vector
  database is not automatically optimal; `sqlite-vec` is compact and portable but explicitly
  pre-v1, so compatibility and migration risk must be scored.

Every selected dependency and model must be rechecked at execution time for current release status,
license, signed/checksummed distribution, platform support, security advisories, and project health.

## Success Budgets And Quality Floors

M2 freezes exact benchmark methodology before selection. The following are initial hard ceilings;
loosening one requires a separately approved backlog task and recorded maintainer decision.

| Area | Required floor or ceiling |
| --- | --- |
| Hardware | CPU-only operation on the i5-7200U/7.1 GiB baseline; no AVX-512, GPU, NPU, or hosted inference requirement. |
| Local artifacts | Selected chat model, embedding model, indexes, and required runtime assets total at most 2.5 GiB on disk. |
| AI memory | Peak RSS attributable to the model, embedding, and retrieval workers is at most 3.5 GiB at one active conversation; disabled mode starts no AI worker. |
| Lexical search | P95 result render is at most 250 ms on the baseline and all existing deterministic search fixtures pass. |
| Chat retrieval | Warm same-locale local-evidence retrieval for an enabled chat is at most 2 seconds P95; it is independent of ordinary documentation search. |
| Generation | Warm time to first token P95 is at most 10 seconds, cold time to first token P95 is at most 30 seconds, and median generation is at least 3 tokens/second for the frozen short-answer scenario. |
| Answer completion | A cited answer capped by the accepted output budget completes within 60 seconds P95 on the baseline; stop/cancel remains responsive. |
| Lexical search quality | A candidate or revision is no worse than the frozen previous-version control for Top-1, MRR, Recall@5, no-result handling, and every exact identifier in each locale; it demonstrates a strict relevance improvement in each locale before replacing that control. |
| Grounding | Every displayed citation resolves; at least 95% of scored answer claims are supported by cited current sources; unsupported-answer abstention is at least 95% per locale. |
| Scope gate | 100% of the reviewed off-topic fixtures are blocked in every locale, in-scope false refusal is at most 2%, and every fixed prompt-injection/tool/file/network escape fixture fails closed. |
| Privacy | Local mode emits no query, conversation, chunk, embedding, or model telemetry and makes no network request after explicit model installation. |

## Non-Goals And Assumptions

- Do not turn the assistant into a general-purpose chatbot, coding agent, browser automation agent,
  profile editor, or policy executor. It cannot mutate profiles, import/export files, run commands,
  access arbitrary files, call arbitrary URLs, or change BPM settings.
- Do not make AI availability a prerequisite for documentation. Lexical search, navigation,
  contextual links, and direct topics remain fully usable when models are absent, disabled, loading,
  incompatible, crashed, or too slow.
- Do not require cloud inference, a hosted vector database, a hosted search service, an account, an
  API key, telemetry, or a GPU for the core `0.9.3` assistant.
- Do not commit model weights, generated embeddings, generated search indexes, chat transcripts,
  downloaded web pages, build output, or benchmark reports outside their approved ignored/package
  artifact boundaries.
- Do not silently download a model or accept model terms. Installation is explicit, checksummed,
  license-visible, resumable, and removable; offline installation from a verified local artifact is
  supported.
- Do not fine-tune a base model on raw DITA merely to call the result “trained.” Normal product
  evolution uses deterministic chunking, embeddings, and incremental re-indexing. A versioned
  LoRA/adapter path is optional only if a later benchmark proves retrieval and prompting insufficient;
  it is not trained on the target laptop and cannot weaken citation, provenance, or locale gates.
- Do not allow the model to invent product support, Firefox policy semantics, CIS claims, API
  guarantees, or procedures. When current local evidence is insufficient or contradictory, the
  assistant asks for clarification or abstains.
- Do not use unreviewed AI output as maintained DITA or localization. Existing human review,
  provenance, terminology, placeholder, parity, screenshot, and editorial gates remain authoritative.
- Do not use cross-locale retrieval or fallback for chat. The chat resolves the user's active locale
  and retrieves only its corresponding local documentation; language-neutral technical identifiers
  remain attached to that locale's evidence.
- External web retrieval is disabled by default and is never necessary for local BPM questions.
  When enabled, local BPM documentation outranks web evidence and conflicting web facts are labelled,
  not silently merged.
- Search-engine and model names in this backlog define a shortlist only. Selection occurs after the
  approved reproducible benchmark, and existing behavior stays in place until its replacement passes.
- README changes occur only after implementation and only for durable installer/user/administrator
  facts. README receives no target-version marker, release history, or completion placeholder.

## Execution Protocol

When executing this backlog interactively:

1. Show exactly one next task with its ID, essence, acceptance, minimum model, and minimal reasoning.
2. Wait for explicit maintainer approval.
3. Execute only that approved task.
4. Report changed files, artifacts, measurements, and checks passed.
5. Show the next task for approval.

For a long-running command, show flushed interactive progress in that command's own output, based
on real work units such as phase/locale, completed/total units, cache or retry state, and terminal
success/failure. Do not use synthetic percentage, spinner, or guessed ETA. Keep chat silent while
the command runs; if its native output cannot expose progress, provide a read-only task-owned
observer. Preserve safe interruption, partial-artifact quarantine, and atomic promotion.

An approval automatically authorizes the agent to request and use every task-scoped execution
permission needed to satisfy that task's acceptance criteria. This includes immediate sandbox
escalation for browser/Selenium commands, temporary loopback listeners, verified temporary
downloads and artifact installation, and removal of agent-created temporary artifacts. The agent
must request a protected permission before the command and must not make a restricted trial first.
This authorization does not cover external account creation, acceptance of non-standard third-party
terms, access to secrets outside the ordinary task configuration, mutations outside the approved
task, or committing/pushing without separate task approval.

Do not start implementing a backlog task merely because this backlog exists. Technology shortlist
entries do not authorize a dependency install, model download, web-provider account, network call,
or model-license acceptance before the corresponding task is approved.

Browser/Selenium commands must be run with immediate sandbox escalation during backlog execution;
do not attempt a sandboxed browser run first. Do not push from backlog execution. Create the final
commit only when its task is separately approved, then print the exact push command for the
maintainer.
